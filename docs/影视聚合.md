# 影视聚合（/tv）

站内常驻功能页：聚合多个公开的「苹果CMS / MacCMS V10」采集接口，一处搜索、
跨源合并、点开即播，另带 IPTV 直播频道。

- 页面：`/tv`（只有中文形态，见下方「为什么不走 `[...locale]`」）
- 接口：`/api/tv/*`（六条只读 GET，在 `src/worker.ts` 里分发）
- 代码：`src/lib/tv/`（服务端）、`public/tv/`（客户端）、`src/styles/tv.css`（样式）
- 入口：`/tools` 页的第三张卡（仅 `locale === 'zh'` 时渲染，与「步数管家」同一条规矩）

---

## 一、说清楚它是什么、不是什么

**是**：一个只做检索与播放的客户端。它向第三方公开接口要「影片列表 / 剧集地址」，
把地址整理成浏览器能播的样子，然后让浏览器自己去 CDN 取流。

**不是**：不托管、不转存、不分发任何视频内容；不提供任何片源；不内置任何
「片库」。片源与合法性由对应的第三方接口负责，接口失效就在
`src/lib/tv/sources.ts` 里删掉那一条。

正因如此：

- 这一页在 `public/_headers` 里配了 `X-Robots-Tag: noindex, follow` ——
  它是工具页，不该被搜索引擎当成站点内容收录，也不该替那些源站做 SEO。
  要放开就删那两行。
- 它不进 `sitemap`（与 `/admin` 同一个理由：`astro.config.mjs` 里排除）。
  **注意**：`/tv` 是根路径页面、不在 `[...locale]` 下，所以**不会**被 sitemap 自动收录 ——
  这一条无需额外配置，写在这里是为了让后来的人不用去查。

## 二、为什么媒体字节不进 Worker（以及为什么直连必须排第一）

`src/worker.ts` 顶部的规矩是「不中转媒体字节」，音频与封面都让浏览器直连。
这一页沿用同一条，并且有实测依据（2026-10，逐个源验过响应头）：

| 源 | m3u8 的 ACAO | 分片 `.ts` 的 ACAO |
| :--- | :--- | :--- |
| 极速 / 量子 / 电影天堂 / 光速 / 暴风 / 百度 / 无尽快 | `*` | `*` |
| 最大资源 | `*` | **无** ← 唯一例外 |

播放走**三级降级链**（`public/tv/app.js` 里的 `TRIES`），顺序不能调换：

| 级 | 做什么 | 谁去取流 |
| :--- | :--- | :--- |
| 1 `direct` | 把上游 m3u8 **原样**交给 hls.js | 浏览器 → CDN，**Worker 零参与** |
| 2 `hlsProxy` | 经 `/api/tv/hls` 取播放列表并改写 URI 为绝对地址 | Worker 取列表，浏览器取分片 |
| 3 `fullProxy` | 连分片也经 `/api/tv/seg` 转发 | 全走 Worker（最慢，最后手段） |

> **坑（现象 → 根因）｜2026-10-20 上线后实测发现**
>
> **现象**：本地 `wrangler dev` 下 15 个源全部能取到播放列表；部署到 Cloudflare 后，
> 同一条探针只有 **7/15** 能取到，其余 8 个报 `上游返回 HTTP 403 / 404 / 530`。
> 而同一时刻、同一组 m3u8 地址，从家中宽带网络直接 GET 是 200。
>
> **根因**：那 8 个源的 m3u8 CDN 对 **Cloudflare 机房出口 IP** 直接拒绝
> （403 防盗链 / 404 路径拒 / 530 源站错误）。而点播搜索与详情用的 `api.php` 接口
> 完全不拦，所以「能搜到、能点开、一点播放就失败」，症状很像源站挂了，实际不是。
>
> **修法**：把 `direct` 提到第一级。这些 m3u8 本身带 `Access-Control-Allow-Origin: *`，
> 浏览器从**访客自己的网络**去取是通的；hls.js 拿到原始 m3u8 后会自动以该地址为基准
> 解析里面的相对路径，所以直连时**不需要我们改写任何 URI**。
> 改写只在第 2、3 级（走代理）时才必要。
>
> **这条修完后的实测**：CDP 驱动真实 Chromium 打开线上页、点第一张卡、点第一集，
> `video.readyState=4`、`videoWidth=1280`、`currentTime` 在走 —— 且成功的正是
> 前述 8 个「Worker 取不到」的源之一（UKU 资源）。**所以以后改这一块，
> 验收必须以浏览器能否出画为准，不能以「Worker 能不能 curl 到 m3u8」为准。**

除了降级链，还有两件必须做的改写，只在第 2/3 级发生：

- **相对路径**：m3u8 里的路径几乎全是相对的（`2000k/hls/mixed.m3u8`）。一旦播放列表
  经本站代理，浏览器的解析基准就变成本站，会被拼成
  `https://本站/api/tv/2000k/hls/mixed.m3u8` 而 404。这就是第 2 级要改写的原因。
- **`EXT-X-KEY` 的密钥**：AES-128 加密流的 key 同样是相对路径，`rewritePlaylist()`
  里那条 `URI="…"` 的正则就是干这个的。漏了它的表现是「能播但一直转圈」。

## 三、搜索逻辑（改行为先读这段）

实现在 `src/lib/tv/cms.ts` 顶部有一段完整注释，这里只列要点：

1. **并发 + 单源死线**：15 个源同时发，每源 6.5 秒硬死线（`AbortSignal.timeout`）。
   用 `Promise.allSettled`，失败只丢那一个源，并在返回里如实列出「未响应」。
2. **自适应翻页**：`ac=videolist` 返回 `pagecount`。翻页是每源多一次请求，
   而 Workers 免费档一次请求最多 50 个 subrequest —— 15 源 × 2 页 = 30 个已经接近上限，
   所以 `search()` 里按 `targets.length × maxPagesPerSource ≤ 40` 判：源多时只抓第一页。
3. **熔断**：源连续失败 2 次就冷却 5 分钟（isolate 内存表，不持久化）。
   被冷却的源在返回里标成「暂时停用（近期连续失败）」，不让用户以为只有几个源。
4. **跨源融合**：按 `normTitle()` 归并 —— 去空格、去标点，只留中日韩字符与字母数字。
   **年份不参与分组**：同名不同季在源站本来就是不同 vod，靠标题里的「第二季」区分；
   把年份放进 key 会把「同剧不同源年份转录不一致」的情况拆成两张卡。
5. **打分**：相关性（精确 100 / 前缀 80 / 包含 60 / 其它 20）+ 源命中数×5 + 有可直连
   m3u8 加 15 + 有海报加 3 + 备注含「已完结/全N集」加 6。目标是**第一张卡就能播**。
6. **线路上可播性判定**（`classifyLine()`）：按 URL 形态判，不按名字猜。
   - `.m3u8` → `hls`（可直连，排最前）
   - `/share/…`、`/play/<id>` → `page`（网页播放器页，播不了，UI 标 ⚠）
   - **`v.qq.com` / `iqiyi.com` / `youku.com` / `mgtv` / `bilibili` … → `page`**
   - 其它 → `unknown`

## 四、源清单：只留「真的能播」的

`src/lib/tv/sources.ts` 里 16 个点播源 + 4 个直播源，全部在 2026-10 逐个走过
「搜索 → 详情 → 播放列表」三段验证。判据不是 HTTP 200，而是**确实能取到 `#EXTM3U`**。

**为什么只有 16 个**：探测了 195 + 59 个候选主机，可用的不到 40 个，去重掉大量镜像
（`ffzy3/4/5.tv`、`api.ffzyapi.com` 是同一家；`p2100.net`、`www.wyvod.com`
与 `api.wujinapi.com` 同源 `v6.ppqrrs.com`；`hhzyapi.com` 与 `haohuazy.com` 同源）。
镜像全加进来只会让搜索多花一倍请求、多等一倍延迟，结果一模一样。

被剔除的两个典型（都是「看着能用、点了才发现不能播」，比直接挂掉更坑）：

| 源 | 现象 | 根因 |
| :--- | :--- | :--- |
| `360zy.com` / `360zy.tv` | 列表通、3 条正常，详情无 m3u8 | 片源 CDN `vod2.maowushi.com` 已 502 |
| `hong.hgyx.vip`（红果） | 列表通、单页 13 条最多，集数齐全 | 两条线路分别指向**腾讯视频与爱奇艺官网剧集页**（`v.qq.com/x/cover/…`），要会员登录，`<video>` 永远播不出 |

第二条直接促成了 `classifyLine()` 增加「正版平台域名 → `page`」这条判断。

### 4.1 清晰度是「按片」变的，不是「按源」变的

2026-10-20 第三轮又实测了 59 个候选（含从 TVBox 配置仓库挖出来的 44 个真实接口）。两个结论：

1. **仍然没有真 4K。** 全场唯一接近的是 `www.mdzyapi.com` 的 `3840x1608`，
   而 `3840x2160` 才算 4K；它是宽画幅塞进 3840 容器。**这批 MacCMS `provide/vod`
   采集源的天花板就是「1080p 高码率」**，要 4K 只能走网盘/磁力这类非 `provide/vod` 源。
2. **同一个源对不同片子清晰度差很多。** 实测：

   | 源 | 流浪地球2 | 阿凡达 |
   | :--- | :--- | :--- |
   | 360 资源（本轮新增） | 1280×538 / 706 kbps | **1920×1080 / 6733 kbps** |
   | 光速资源 | 1920×1080 / 4096 kbps | 1920×1080 / 4096 kbps |
   | 摩都资源 | 3840×1608 / 2000 kbps | 1920×1080 / 6733 kbps |
   | 量子资源 / 非凡资源 | 1080×608 / 800 kbps | 1080×608 / 1080p |

   所以「哪个源清晰」**没有固定答案**，只能按片实测 —— 这正是 9.1 那套前端探测存在的理由。
   `360 资源` 因此加入清单：它在部分片上给出全场最高的 6.7 Mbps 码率；
   探不到时（该片的线路挂了）它自然得 0 分、不会被选中，加进来没有副作用。
3. **`cj.lziapi.com`（量子资源）实测只有 1080×608**，是被抱怨「不够清晰」的主力嫌疑。
   保留它是因为它偶尔有新片，但**排序会把它压到后面** —— 自动选源不会选中它。

## 五、为什么不走 `[...locale]`、为什么样式不写颜色

**不走语言路由**：与 `/bushu` 同一条理由 —— 这一页只有中文形态，挂到 en/ja 下
等于把用户送进一页看不懂的界面。所以它是根路径页面，`getStaticPaths` 那套用不上。

**样式只用站点变量**：`src/styles/tv.css` 里没有一处硬编码颜色，全部取
`--paper` / `--ink` / `--seal` / `--rule` / `--font-*` / `--sp-*`。于是四套版次
（夜刊 / 晨版 / 胶片 / 霓虹）自动成立，换版次不用改这一页一个字。
**这是本页的验收项之一：四套版次都实际看过。**

## 六、三条容易踩的实现规矩

1. **`[hidden]` 必须自己压过类里的 `display`**。`.tv-drawer` / `.tv-player` 都写了
   `display: flex`，而作者样式优先级高于 UA 的 `[hidden]{display:none}` ——
   少了 `[hidden]{display:none !important}`，抽屉和播放器会一直挂在页面上。
   （这个坑在别的项目里已经踩过一次，这次是提前防的。）
2. **客户端入口挂 `astro:page-load`，不是 `DOMContentLoaded`**。全站走 ClientRouter，
   `public/tv/app.js` 是 `is:inline` 的普通脚本，首次执行一次就再不会重跑；
   进 `/tv` → 离开 → 再进来，DOM 是新的、绑定是旧的。所以 `boot()` 挂在
   `astro:page-load` 上，并用 `root.dataset.tvReady` 防重复绑定。
3. **`run_worker_first` 只加 `/api/tv/*`，不要加 `/tv`**。那一页是构建产物里的静态
   HTML，交给 ASSETS 发比过一遍 Worker 更快、也更少一个故障点。

## 七、怎么验

```bash
npm run build && npx wrangler dev --port 8788
```

`astro dev` 下 `/api/tv/*` 必然 404（没有 Worker 运行期），在那里测等于没测 ——
这与 `docs/开发约定.md` 里关于 `/api/music/*` 的那条一致。

跑起来之后：

| 验什么 | 怎么验 |
| :--- | :--- |
| 搜索 + 融合 + 打分 | `curl "http://127.0.0.1:8788/api/tv/search?q=庆余年"` → 看 `sources[].ok` 与 `groups[].score` |
| 线路可播性排序 | `/api/tv/detail?s=js&id=<vodId>` → `lines[0].kind` 应为 `hls` |
| 播放列表改写 | `/api/tv/hls?u=<m3u8>&ref=<origin>` → 每一行 URI 都应是 `http…` 绝对地址（这只验第 2 级） |
| SSRF 守门 | `/api/tv/hls?u=http://127.0.0.1/x.m3u8` → 应返回「内网地址不允许」 |
| 直播 | `/api/tv/live` → 四个源合计约 1500 频道（zbds 的 txt 与 m3u 两种格式都要解析成功） |
| **能不能真出画** | **必须用浏览器验**（见下），不能用 `/api/tv/hls` 的 200 代替 |
| 视觉 | 四套版次各看一眼；深浅都要看（`docs/开发约定.md` 的验证纪律） |

### 关于「能不能真出画」的验收

`/api/tv/hls` 返回 200 **不等于**能播 —— 它只证明 Worker 这一侧取得到播放列表。
2026-10 那次就是：Worker 侧只剩 7/15，而用户浏览器里其实大半能播（因为走第 1 级直连）。

所以真正的验收是驱动一个浏览器点进去看 `<video>`：

- 打开 `https://duchenlin.top/tv?q=庆余年`
- 点第一张卡 → 选一条不带 ⚠ 的线路 → 点第一集
- 判据：`video.readyState === 4`、`videoWidth > 0`、`currentTime` 在增长

这条可以用 CDP（`--remote-debugging-port`）脚本化，不必手点。**线上那次就是这么做实的**：
一次通过，`1280x720`，成功命中的还是「Worker 取不到播放列表」的那个源。

## 八、扩展与调整

- **加源**：往 `VOD_SOURCES` 里加一条 `{ id, name, api, note }`。`api` 必须以
  `/api.php/provide/vod/` 结尾带斜杠。加完务必走一遍「搜索 → 详情 → 取播放列表」，

  txt 两种格式自动识别（`parsePlaylistText()`）。

## 九、清晰度、自动选源、记录（2026-10-20 起）

### 9.1 清晰度只能实测，而且要在浏览器里测

资源站 API（`ac=videolist` / `ac=detail`）**没有任何分辨率字段**。唯一可信来源是
master 播放列表里的 `RESOLUTION=` / `BANDWIDTH=`。所以：

- **后端**：把每个候选源的「首条可直连 HLS 地址」放进搜索结果（`Candidate.firstHlsUrl`）。
  `ac=videolist` 响应本来就带 `vod_play_url`，所以这不算多打一次请求 ——
  否则前端要为 15 个候选各发一次 detail，再多发 15 次 m3u8，太重。
- **前端**：拿到地址后**在浏览器里**并发探测前 6 个（`PROBE_TOP_N`），
  解析 master 的 `RESOLUTION` 取最大，顺带用「整份播放列表的下载耗时」当测速代理。
  结果按 `sourceId:vodId` 缓存进 localStorage 7 天。

> **为什么探测放在浏览器而不是 Worker**：与第二节同一个原因 ——
> 这些 m3u8 CDN 对 Cloudflare 机房出口 IP 会回 403/404/530，对访客浏览器放行。
> 放在 Worker 里探测，会有一半源测不出来。

### 9.2 自动选源：清晰度优先，速度为次

打分是 `宽 × 1e6 + 带宽/1e3 − 延迟毫秒`，即**分辨率压倒一切**，同分辨率才比带宽和延迟。
实测行为：搜「庆余年」时它选了 `光速资源 1080P / 783ms`，
而不是 `电影天堂 608P / 307ms` —— 快但更糊的不会被选中。

探测完成后会**自动切到最优源一次**（`state.autoPicked` 保证只切一次，不跟用户手动选择抢）。
详情页顶部会显示「已测 N 源 · 最高 1080P」。

### 9.3 清晰度切换按钮的真实价值：很低

播放器里用 hls.js 的 `levels` 做了清晰度切换（自动 / 各档）。但**实测这个按钮基本不会出现**：
对 8 个源逐个取 master 列表看 `#EXT-X-STREAM-INF` 条数，全部是 **0（纯媒体列表）或 1（单变体）**，
**没有一个源提供多码率**。也就是说：

- 这些资源站的清晰度**上限就是 1080p**，没有自适应码率可选；
- 按钮保留着（多码率一旦出现就有用），但别指望它 —— 想换清晰度只能换源。

### 9.4 「超高清晰度」的现实：现有源池没有真 4K

2026-10-20 对 96 条源记录做了分辨率实测（读 master 的 `RESOLUTION`），结论：

| 结论 | 数据 |
| :--- | :--- |
| 有分辨率数据的记录 | 27 / 96 |
| ≥1080p 的源 | 6 个 |
| **真 4K（≥约 3800×2100）** | **0 个** |

最高的那条是 `www.mdzyapi.com` 的 **3840×1608** —— 面积 6.17M 像素，
而 3840×2160 是 8.29M。**这是宽画幅影片被塞进 3840 宽的容器，不是 4K**。
所以「要 4K」不是播放器或播放链路的问题，是**源本身没有**。
要么接受 1080p 上限，要么继续找真的 4K 采集源（另开一轮筛选，判据就用本节的实测方法）。

### 9.5 本地记录：搜索历史 / 播放历史 / 断点续播

全部存 `localStorage`（**匿名可用，不依赖登录**）：

| 键 | 内容 | 上限 |
| :--- | :--- | :--- |
| `tv:q` | 搜索历史 `[{q,t}]` | 12 条，搜索框下方展示，可一键清空 |
| `tv:prog` | 播放进度 `{ "片名\|\|集名": {t,d,ts,srcId,vodId,lineIdx,...} }` | 30 条 |
| `tv:qual` | 清晰度探测缓存 | 200 条 / 7 天 |
| `tv:off` | 访客关掉的源 | — |

行为：

- 搜索框下方出现「最近搜过」，点一下直接再搜；
- 首页出现「继续观看」，点它 → 再搜同名 → 命中就自动开详情；
- 详情页若该片有进度，显示「上次看到第 X 集（60%）」+「继续播放」按钮；
- 看过一点的剧集按钮上有个小圆点；
- 播放中每 5 秒 + 暂停/结束落盘；再次点开同一集会**自动跳回上次位置**并 toast 提示
  （已快看完的不续播，从头更合理）。

> 这些是**本机**记录，换设备/换浏览器就没了。要做到跨设备、且按用户隔离，
> 需要服务端存储 + 登录 —— 即下面的第九节，尚未实现。

### 9.6 结果排序：可按评分重排（第三轮）

资源站接口没有统一的评分字段，但 MacCMS 有 `vod_score`。`fuse()` 里取各源**最大值**
写进 `Group.rating` —— 注意它和排序打分 `Group.score` 是两个字段，别混：

- `score`：服务端算的相关性打分，「推荐」排序用它；
- `rating`：影片评分，「评分」排序用它。

前端排序条四档：**推荐 / 评分 / 源最多 / 名称**，选择存 `localStorage['tv:sort']`。

实测「庆余年」：推荐首条是「庆余年 第二季」；切「评分」后首条变「庆余年之风起沧州」，
评分序列 `10,10,10,10,9,9` —— 排序确实生效。

⚠️ 不是所有源都填 `vod_score`（很多是空或 `0.0`），所以评分排序只在有数据的片上有效，
不要指望它对每部片都合理。

### 9.7 播放倍速：长按右箭头 3×

- 按住 `ArrowRight` → `playbackRate = 3`，松手回到常驻倍速。
- **必须 `preventDefault()`**：浏览器对右箭头的原生行为是「快进 5 秒」，
  不拦的话「按住」会变成一路跳着走，而不是快放。
- 另有常驻倍速按钮，点按轮换 `1× / 1.5× / 2× / 3×`；换集或换源后回到常驻档，
  **不沿用**上一次长按的临时快放。
- 实测：`1 → 按住 3（按钮变色）→ 松手 1`。

### 9.8 记录上云（仅登录用户）

匿名走 localStorage（9.5）；登录用户的记录走云端，跨设备可用。
合并规则与接口见 [站点账号](站点账号.md) 第七节。前端只有一条纪律：
**`/api/tv/hist` 返回 401 就静默跳过**，不能让未登录的人看到报错。
