# 技术架构

## 选型与理由

| 层面 | 选择 | 为什么 |
| :--- | :--- | :--- |
| 站点框架 | Astro 7 | 默认零 JS 输出，博客这类内容站首屏最快；内容集合（Content Layer）带类型校验，frontmatter 写错在构建时就报错，不会上线后才发现空白 |
| 内容格式 | Markdown / MDX | 纯文本、可版本控制、不锁定平台 |
| 托管 | Cloudflare Workers 静态资源模式 | 不是 Pages。裸域绑定、证书、CDN 一体，免费额度足够个人站。**2026-08-22 起同一个 Worker 还带一条 `main`**，见下「服务端」一节 |
| 图片 | Astro 内置 `sharp` | 构建时压缩、转 WebP、生成多尺寸，写作时不用手工处理图片 |
| 代码高亮 | Shiki 双主题 | 构建时高亮，运行时零成本；深浅主题切换靠 CSS 变量，不需要重新高亮 |
| 数学公式 | KaTeX + remark-math | 比 MathJax 轻，样式与字体自托管 |
| 部署工具 | Wrangler | 本地一条命令部署，不依赖 CI |

## 硬约束

**不引用任何境外 CDN 资源。** 站点托管在境外，国内访问时请求数比字节数更影响首屏。
所以：

- 西文字体（Fraunces 可变字体 / IBM Plex Mono）随构建产物分发；
- 中文**不加载任何字体**，走系统字体栈（零加载成本，这是中文站最大的性能杠杆）；
- KaTeX 的样式与字体自托管；
- 后续加任何第三方能力，先确认能否构建时内联或自托管。

## 服务端：`/api/music/*`（点歌台）

本站原先没有一行服务端代码。**2026-08-22 起 `wrangler.toml` 有了 `main = "src/worker.ts"`** ——
这道「单向门」第 11 轮已批准，由 [R11 点歌台](需求台账.md#r11-点歌台-) 提前走完。

```
GET /api/music/list?id=<白名单榜单 id>         → { items: JukeTrack[] }
GET /api/music/search?q=<关键词>&n=<1..30>     → { items: JukeTrack[] }
GET /api/music/url?id=&source=&sign=           → { url }
GET /api/music/lyric?id=&song=&source=&sign=   → { lyric, tlyric }
```

四个要点：

- **只有这四条进 Worker**。`run_worker_first = [ "/api/music/*" ]`，其余请求连 Worker 都不唤起
  （省调用数，也少一个故障点）。即便如此，`fetch` 的第一行仍然兜一道：路径不以 `/api/music/`
  开头就 `return env.ASSETS.fetch(request)` —— 官方文档没写清 `not_found_handling = "404-page"`
  与「数组之外的路径是否仍进 Worker」的优先顺序，不赌。
- **Worker 只中转 JSON，音频字节不经过它。** 这是容量前提：直链是 https、
  `Access-Control-Allow-Origin: *`、支持 Range，浏览器直接从 `music.126.net` 拉，一首歌
  13 MB 一个字节都不进 Worker 配额；Worker 转的只是几百字节到几十 KB 的 JSON。
  **不要改成中转音频。**
- **出口只吐白名单字段**（`JukeTrack`），不原样转发上游 JSON；上游的响应体与错误页一个字都不
  外泄，返回给访客的全是自己写的中文。榜单 id 同样是白名单，否则这就是个「任给 id 就拉网易云
  歌单」的公开代理。
- **缓存头在代码里自设** —— `public/_headers` 不作用于 Worker 生成的响应，边缘缓存显式走
  `caches.default`（Workers 独有的默认缓存区）。逐端点的值见
  [部署运维 · 缓存](部署运维.md#缓存)。

上游契约（`yinyueku.cn/api.php` 的参数表、签名怎么绑 `types`、四条踩过的坑）全部记在
`src/data/jukebox.ts` 的顶部注释里 —— 那是全项目唯一记录它的地方，改 `worker.ts` 之前先看它。

**刻意不引 `@cloudflare/workers-types`**：它的全局 `Request`/`Response` 会和 Astro 的
`lib.dom` 打架，为一个 `Fetcher` 类型换来全站类型冲突不值得。用得到的绑定就地声明成
`interface Env { ASSETS: { fetch(req: Request): Promise<Response> } }` 即可。

**加了 `main` 的代价**：以前构建失败只是不部署、线上不受影响；现在 Worker 抛异常就是线上 500。
所以每条路径都有兜底，`route()` 的异常统一落到 502 加一句人话。

## 设计系统

全部集中在 `src/styles/global.css`，靠 CSS 自定义属性（CSS 变量）分层。改视觉只改变量，
不碰组件。

### 分层

1. **令牌层** `:root` —— 字体、字号、间距（8px 基准）、版心宽度、圆角、颜色、玻璃参数、光晕。
2. **主题层** `:root[data-theme='light']` —— 只覆盖颜色相关令牌。
3. **基础层** —— 重置、排版、链接、滚动条。
4. **工具层** —— `.wrap`（版心）、`.glass`（玻璃面板）、`.meta`、`.vertical-label`、`.rise`（淡入）。
5. **正文层** `.prose` —— Markdown 渲染结果的排版。

### 毛玻璃的三个物理前提

这套效果做不出来时，问题基本都在这三条上：

1. **必须有可折射的底层。** `backdrop-filter` 在纯色背景上完全看不出效果。
   `body::before` 铺的三团径向渐变光晕就是折射源，它是物理基础不是装饰。

2. **光晕层不能溢出视口。** 必须 `position: fixed; inset: 0`。径向渐变的中心写的是百分比，
   按元素盒子解析 —— 元素一旦比视口大，中心就被按比例推到视口外，屏幕上只剩边角余晖。
   **踩过一次。**

3. **`body` 不能有不透明背景色。** `body` 只有 `position: relative`、`z-index: auto`，
   不构成层叠上下文，所以两个负 `z-index` 伪元素落到根（`html`）层叠上下文里。
   在根上下文中负 `z-index` 后代先绘制、`body` 自身背景后绘制 —— `body` 一旦有不透明背景
   就会把光晕层和颗粒层整个盖掉。**底色交给 `html` 承担。**

### 深色玻璃与浅色玻璃的构造是反的

| | 深色 | 浅色 |
| :--- | :--- | :--- |
| 玻璃本体 | 白色半透明**提亮**（`rgba(255,255,255,.045)`） | 白色半透明，但需更实 |
| 外描边 | 白色半透明即可（白压深底，可见） | **必须用深色描边**（白压浅底＝没有描边） |
| 内高光 | 轻微 `inset` 白线 | 强 `inset` 白线，这是立体感来源 |
| 底色 | 越深越好，衬托光晕 | 不能太浅，否则玻璃无对比 |

浅色主题当前的问题正是照抄了深色的构造，详见 [需求台账 R4](需求台账.md#r4-浅色主题下玻璃不明显-)。

### 中文排版决策

- 正文 `17px`（中文舒适下限）、行高 `1.85`（中文比西文需要更大行高）、字距 `0.01em`。
- 文章版心 `38rem`，每行约 33–36 字。
- 标题西文用 Fraunces 衬线、中文落宋体栈 —— 中文编辑排版的经典对比手法。
- 正文中文用黑体栈（屏幕上比宋体耐读）。
- `.prose strong` 用强调色而非加粗：中文没有真正的粗体字形，加粗靠合成，效果差。
- 元信息用等宽 + 全大写 + 宽字距，编辑感的来源。
- `.vertical-label` 竖排中文栏目标识，仅宽屏显示 —— 本站的记忆点。

### 深浅主题切换

读系统偏好作为初值，手动切换后记在 `localStorage`。`BaseHead.astro` 里有一段内联脚本
在样式加载前就写好 `data-theme`，避免刷新闪白。

## 内容模型

四个集合定义在 `src/content.config.ts`，共用字段 `title`、`description`、`pubDate`
（必填，缺了构建报错）、`updatedDate`、`tags`、`draft`、`cover`。

`photos` 额外要求 `cover`，并支持 `images` 数组放组图；`projects` 额外有
`status`（active/wip/archived）、`link`、`repo`。

草稿（`draft: true`）本地可见，构建时排除 —— 过滤逻辑在 `src/utils/content.ts`。

写作字段的完整说明见 [写作指南](写作指南.md)。
