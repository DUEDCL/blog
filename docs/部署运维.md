# 部署运维

## 现状

托管在 **Cloudflare Workers 静态资源模式**（不是 Pages）。**2026-08-22 起不再是纯静态** ——
`wrangler.toml` 有了 `main = "src/worker.ts"`，`/api/music/*` 四条只读 GET 在线上跑
（[R11 点歌台](需求台账.md#r11-点歌台-)），其余路径仍原样交回静态资源。

| 项目 | 值 |
| :--- | :--- |
| Worker 名 | `duchenlin-blog` |
| 绑定域名 | `duchenlin.top`（主域）、`www.duchenlin.top`、`duchenlin.eu.cc`（备用） |
| 服务端代码 | `src/worker.ts`，只有 `/api/music/*`；`run_worker_first = [ "/api/music/*" ]`，其余路径连 Worker 都不唤起 |
| 证书 | Cloudflare 自动签发，两个 zone 均 Active |
| Always Use HTTPS | 两个 zone 均已开启 |
| workers.dev 子域 | **已关闭（2026-08-23）**，连版本预览 URL 一起关。见「已关闭的 workers.dev 入口」 |

DNS 记录和证书都由 `wrangler.toml` 里的 `[[routes]] custom_domain = true` 自动生成，
**不需要手工加任何解析记录**。裸域按 DNS 规范不能用 CNAME，Cloudflare 用 CNAME 展平
（CNAME flattening）在内部解决了这个限制，前提是 DNS 必须托管在 Cloudflare。

## 发布流程

```bash
npm run build && npx wrangler deploy
```

`wrangler deploy` 读的是 `dist/`，所以必须先构建。

**R41 起 `npm run build` 还有第二个产物必须先跑出来**：`scripts/gen-content.mjs` 生成的
`src/data/content.generated.ts`（仓库内容的原样快照，后台的「文章编辑」「图库管理」
就是读它）。它在 `.gitignore` 里，而 `src/worker.ts` **静态引入**它 ——
所以单独跑 `npx wrangler deploy` 而不先 build，会在打包这一步失败（明确报找不到这个 import，
不会静默上错代码）。`npm run dev` 同样会先跑它。

部署需要 `CLOUDFLARE_API_TOKEN` 环境变量，或 `npx wrangler login` 交互授权。

> **凭据实际来自环境变量 `CLOUDFLARE_API_TOKEN`，不是 OAuth 授权。** 这一条 2026-08-23
> 实测纠正了原来的记载（原文写的是「已完成 OAuth 授权，凭据落在 config 文件里」）：
>
> - `npx wrangler whoami` 报的是 *"You are logged in with an User API Token"*；拿
>   `CLOUDFLARE_API_TOKEN` 调 `user/tokens/verify` 返回 `active`，**它才是在起作用的那个**。
> - `%APPDATA%\xdg.config\.wrangler\config\default.toml` 里确实有 `oauth_token`，但它**已经失效** ——
>   拿它调 API 返回 `[{"code":9109,"message":"Invalid access token"}]`。`~/.wrangler` 这个目录不存在。
>
> 所以真正的依赖是那个环境变量：**它一旦没了（换机器、清掉环境）就无法部署**，
> 得去 dashboard 重新签一个 token，光看 config 文件里还躺着 `oauth_token` 会误判成「已授权」。
> Token 权限含 `workers:write`、`ai:write`、`ai-search:write`、`d1:write`、`zone:read`，
> 够 R6 全部阶段用；三个 `custom_domain = true` 要求 `zone:read`，缺了会在 deploy 步失败。
>
> 账号是哪一个**不写在这里** —— 本仓库是公开的，账号邮箱等于把 QQ 号挂到公开索引上。
> 同理，token 只提变量名，不写值。


> **wrangler 走本机代理会失败。** 本机 `HTTP_PROXY` 指向 `127.0.0.1:12334`，该代理本身是通的，
> 但 wrangler 走它报 `fetch failed`，直连 `api.cloudflare.com` 正常。部署前需要清掉
> `HTTP_PROXY HTTPS_PROXY http_proxy https_proxy ALL_PROXY all_proxy`。
>
> PowerShell 里清代理（**`unset` 和 `&&` 都不能用**，那是 POSIX shell 语法）：
>
> ```powershell
> Remove-Item Env:HTTP_PROXY,Env:HTTPS_PROXY,Env:ALL_PROXY -ErrorAction SilentlyContinue
> ```

GitHub 自动构建（Workers Builds）**没接 —— 2026-08-23 查完之后明确决定不接**。所以
「推送 ≠ 上线」这件事继续成立：**GitHub 只是代码存放处，线上跑的是最后一次
`wrangler deploy` 推上去的产物。**

不接的理由都是实测的，不是嫌麻烦：

| 本来指望的收益 | 实测结论 |
| :--- | :--- |
| 非生产分支给 preview 地址，上线前先看一眼 | **打不开。** preview 地址在 `*.workers.dev` 上，本机直连时 DNS 解析到 `162.125.32.13` —— 不属于 Cloudflare 的段（主域拿到的是 `172.67.x` / `104.21.x`），TCP 连不上，两次各 15 秒超时；走本机代理报 `schannel: failed to receive handshake`。同一时刻 `duchenlin.top` 直连 200 / 2.17s |
| 出问题回滚更容易 | **本来就能回滚。** Cloudflare 侧存着 10 个 version（`source` 全是 `wrangler`），指定 version 即可回退，跟 Builds 无关 |
| 省掉手工 `npm run build && npx wrangler deploy` 和清七个代理变量 | 这些命令沉麟一次都没手敲过，一直是 Claude 在跑；而代价（`main` 从此是发布分支、推 commit 等于上线、没法推草稿）由他承担 |

**什么情况下回来接**：沉麟打算自己在 GitHub 网页上改 markdown、提交完就自动上线、
不用叫 Claude —— 那时 Builds 是刚需，preview 打不开也无妨。

真要接的时候按这个填，外加一条**顺序上的死规矩**：

1. **先 `git push` 把本地已部署的内容推上去，再去 dashboard 连接。** 反过来会出事 ——
   2026-08-23 当时 `origin/main` 落后本地 6 个 commit（不含点歌台、不含 `main = "src/worker.ts"`、
   不含 `/` 与 `/home` 的新路由）。先连上、再由任何一次推送触发构建，Cloudflare 会拉那份旧代码，
   **线上直接回退成纯静态站**，起始页与点歌台一起消失。
2. Cloudflare → **Workers & Pages** → `duchenlin-blog` → **Settings** → **Builds** → 连接 `DUEDCL/blog`。
3. 构建命令 `npm run build`，部署命令 `npx wrangler deploy`（后者本来就是默认值），
   分支 `main`，Root directory 留空，Build variables 不填，API token 留默认自动生成。
   构建镜像默认 Node 24，满足 `package.json` 的 `engines: >=22.12.0`，**不用加 `.nvmrc`**。
4. 这一步只能在 dashboard 里点，Claude 做不了 —— GitHub App 的安装授权只能走浏览器。
   Builds 的 REST API 确实存在（`/accounts/{id}/builds/repos/connections` 一类端点返 **403 +
   `documentation_url`** 而不是 404），但当前 token 没有对应权限，而加权限本身也要进 dashboard，
   所以走 API 并不更短。

**由此定下一条约定：每次 `wrangler deploy` 之后要把代码 push 上去。** 不接 Builds 就意味着
GitHub 与线上是两条各自更新的路径，落差会自己长大；上面第 1 条那个差点回退的场面，
根因就是落差攒到了 6 个 commit 没人发现。

> **git 与 wrangler 对代理的表现是相反的，两者的结论不能混用。** git 配置里有
> `http.proxy = http://127.0.0.1:12334`，`git push` **走这个代理是通的**；wrangler 走同一个
> 代理却必然 `fetch failed`。所以「git 推送成功」推不出「网络直连没问题」，反之也不成立。

## 双域名同步

**涉及域名的改动，两个域名一律同时更新。** 改动点固定 4 处：

| 文件 | 字段 | 填什么 |
| :--- | :--- | :--- |
| `astro.config.mjs` | `site` | **只填主域** `https://duchenlin.top` |
| `src/consts.ts` | `SITE_URL` | **只填主域**（canonical 只能有一个） |
| `wrangler.toml` | `[[routes]]` | **三个域名全列上** |
| `src/content/projects/this-site.md` | 标题与 `link` | 主域 |

改完 `npm run build && npx wrangler deploy`，然后**对两个域名分别验证**。

## 再加一个域名

1. 在 Cloudflare 加站点（Free 套餐），记下它给出的**两台 NS**。
2. 到域名注册商把 NS 改成那两台。
3. 等状态变 Active，然后在 `wrangler.toml` 加一段 `[[routes]]` 并重新部署。

> **NS 是按 zone 随机分配的，两个域名拿到的不是同一对。** 照抄另一个域名的 NS 会导致
> 永远激活不了：那两台服务器上没有你这个 zone 的数据。踩过一次 —— `duchenlin.top` 填了
> `duchenlin.eu.cc` 的 `alfred`/`itzel`，而它自己分到的是 `gloria`/`watson`。
>
> 另外：任何一个 `[[routes]]` 对应的 zone 还是 pending，**整个 `wrangler deploy` 都会失败**，
> 不是只跳过那一条。

## 关于 `duchenlin.eu.cc`

留着当第二入口，但**国内访问不了** —— 有中间设备按主机名字符串匹配注入 TCP RST，
换 IP、换端口、换子域名都绕不过（判据是主机名本身）。境外可正常访问。

这不是配置问题，无法从我们这一侧修复。主域用 `duchenlin.top`。

## 已关闭的 workers.dev 入口

**2026-08-23 关掉了 workers.dev 路由和版本预览 URL 两项**，此后本站只能从三个自定义域名进。

原因是 `<name>.<账号子域>.workers.dev` 里那段**「账号子域」不由我们取名，它的取值本身就是
一条账号标识**（与账号邮箱同类）—— 等于把账号信息挂在一个公开可访问的域名上。这跟
「账号邮箱不写进公开仓库」是同一条原则，只是这次泄漏点在域名而不在文档里。原来留着它的
理由是「DNS 还没生效时用它先验证站点」，三个域名都 Active 之后这个理由已经不存在。

**两个开关是独立的，只关一个不够。** 依据是 wrangler 自己的源码
（`getSubdomainValues()`：`defaultPreviewUrls = undefined`）—— **不写 `preview_urls` 时
`deploy` 压根不去动这个开关**，于是只关 `workers_dev` 会留下
`https://<VERSION_PREFIX>-<name>.<账号子域>.workers.dev` 这条按版本自动生成的公开链接。
wrangler 对这种混合状态会主动发警告，原文：*"you may want to disable the Preview URLs as well
by setting `preview_urls = false`"*。

怎么关的：**先调 API 立刻生效，再改配置文件防止下次部署翻回来。**

```bash
# 立即生效，不需要重新部署（当时工作区有 R14 阶段⑤ 的半成品，部署会把它一起推上线）
curl -X POST -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"enabled":false,"previews_enabled":false}' \
  "https://api.cloudflare.com/client/v4/accounts/<id>/workers/scripts/duchenlin-blog/subdomain"
```

`wrangler.toml` 里同步写上 `workers_dev = false` 与 `preview_urls = false`。顺带一条：
`defaultWorkersDev = routes.length === 0`，本站有三条 `[[routes]]`，**所以 `workers_dev` 的默认值
本来就是 false**，当初那句 `workers_dev = true` 是主动打开的。

验证：`GET .../workers/scripts/duchenlin-blog/subdomain` 与
`GET .../workers/services/duchenlin-blog/environments/production/subdomain` 两条路径都返回
`{"enabled":false,"previews_enabled":false}`；同一时刻 `duchenlin.top`、`www.duchenlin.top`
与 `/api/music/list` 全部 200，三条自定义域名仍在列。

> **未能核实**：本机连不上 `*.workers.dev`（就是上面「发布流程」里那个 DNS 污染），
> 所以「境外访问那个子域是否真的已经 404」没法自己验 —— 只能凭 API 返回的 `enabled: false`。

## 缓存

`public/_headers` 给哈希文件名的静态资源加了长效缓存头，并给 HTML 加了边缘缓存头。

**已部署实测（2026-08-20 Version `942b25ae` 首测，2026-08-22 Version `d58a3c20` 复验）**：

| 资源 | `Cache-Control` | 实测 |
| :--- | :--- | :--- |
| HTML | `public, max-age=60, stale-while-revalidate=604800` | `CF-Cache-Status: HIT` |
| `/_astro/*`（哈希名） | `public, max-age=31536000, immutable` | 命中（新哈希首次请求是 MISS，第二次起 HIT） |

边缘与浏览器各存 60 秒，过期后 7 天内边缘直接吐旧的并后台刷新，访客不等待。国内首屏
1–5 秒的问题因此解决。

**R14 阶段⑥ 补测掉一条一直挂着的未核实项**（先在本机 `wrangler dev` 8788 上测，
部署后 Version `d58a3c20` 在线上复验，两处结论一致）：`_headers` 里 `/xxx/*` 形式的 splat
**吃空串**，`/posts/` 与 `/home/` 都拿到了上表那套 HTML 头（线上 `CF-Cache-Status: HIT`），
所以栏目首页不必再单独写精确规则。同一轮 curl 顺带照出一个真空档 —— `/music/` 只有
`public, max-age=0, must-revalidate`，也就是没有任何规则命中：`_headers` 从来没给
`/music/*` 写过规则，音乐页吃的是 Workers 静态资源的默认头。站上唯一的常驻功能页
反倒是全站唯一吃不到 60 秒 + 7 天 SWR 的一页。既有遗漏，补法就是照抄一条 `/music/*`，
等沉麟发话。

> **注意 Cache Rules 对本站不生效。** 官方文档：*"No zone configuration for caching applies to
> Workers Caching. Cache Rules... have no effect on a Worker's cache."* 本站是 Workers 静态
> 资源部署，面板上配 Cache Rule 没有用，只能靠响应头。
>
> **`_headers` 管不到 Worker 生成的响应**（官方文档原文 "Custom headers are not applied to
> responses generated by your Worker code"）。原先这条写的是「一旦 R6 阶段②加了 `main`……」
> 的未来式，**现在已经是既成事实** —— 2026-08-22 [R11 点歌台](需求台账.md#r11-点歌台-)
> 加了 `main = "src/worker.ts"`。

### `/api/music/*` 的缓存头（由 Worker 自设）

上面那张表**只管静态资源**。点歌台的五条接口不受 `public/_headers` 约束，缓存头在
`src/worker.ts` 里逐端点写死：

| 端点 | `Cache-Control` | 为什么 |
| :--- | :--- | :--- |
| `/api/music/list` | `public, max-age=300` | **歌单是活的**（R23 从 3600 降下来的：沉麟往「沉麟推荐」里加一首歌，不该等一小时才在站上看见；`wrangler dev` 下这层缓存由 miniflare 持久化到 `.wrangler/state/v3/cache/`，**重启进程也不清**，一小时的 TTL 在本地开发里就是一小时看不见改动） |
| `/api/music/search` | `public, max-age=300` | 同一个词短时间内会被反复搜 |
| `/api/music/lyric` | `public, max-age=86400` | 歌词不变 |
| `/api/music/pic` | `public, max-age=86400` | 封面直链是长期地址（自带 `max-age=31536000`，路径里没有 token 也没有时间戳），缓存它没有「过期了就没声音」的风险 |
| `/api/music/url` | `no-store` | 直链路径里带时间戳。R14 实测同一个 URL 连测 6 分钟仍全是 206，所以「播到一半链接过期」不成立；但**更长的有效期仍未核实**，而且缓存它等于把一条会过期的链接发给后来的人，所以照旧不缓存 |
| 任何失败响应 | `no-store` | 不然会把一次上游抖动缓存一整天 |

前端那边配套改了一处：`api()` 的 `fetch` 带 `cache: 'no-store'`，浏览器一律不吃 HTTP 缓存 ——
不然响应头里那条 `max-age` 对它同样生效，「改了歌单刷新看不到变化」会多出第二层原因。
命中与否从此只由边缘那 5 分钟决定，一处可控。

全部带 `X-Robots-Tag: noindex`。命中走 `caches.default`（Workers 独有的默认缓存区），成功且
非 `no-store` 的响应才 `ctx.waitUntil(edge.put(...))`。改这些值只改代码，跟 `_headers`
和面板都没关系。

**首次带 `main` 的部署已线上实测（2026-08-22，Version `d58a3c20`）** —— 在这次部署之前，
点歌台只在本机 `wrangler dev` 8788 上跑过，「线上是否同样成立」属未核实：

| 请求 | 线上结果 |
| :--- | :--- |
| `/api/music/list?id=3778678` | 200，`public, max-age=3600`，`x-robots-tag: noindex` |
| `/api/music/search?q=…&n=6` | 200，`public, max-age=300`，6 条 |
| `/api/music/lyric?…` | 200，`public, max-age=86400`，35 行带时间戳 |
| `/api/music/url?…`（**不带** `name`） | 200，`no-store`，响应只有 `url` 一个字段（择优上线前的行为原样保留） |
| `/api/music/url?…&name=&artist=` | 200，`bytes: 9550125`（≈9.11 MB），首选本身够大所以走快路径、不启动择优 |
| `/api/music/list?id=999999`（白名单外） | 400，`no-store` |
| `/api/music/nope` | 404 |
| `POST /api/music/list` | 405 |
| 15 条站内静态路径 | 全部 200；不存在的路径 404 |

这张表记的是那一天的线上值。**R23（2026-08-23）之后 `list` 是 `max-age=300`**，`pic` 端点
也还没上线过 —— 上表两处与现在的代码不一致是因为它是历史实测记录，不是当前口径。

`swapped` / `short` 这两个标记**本轮线上没有触发条件**：同一次搜索的 6 条候选逐条探测，
5 条拿到 8.04–9.11 MB 的完整文件、1 条 tencent 取不到直链，没有一条的首选小于 2 MB 阈值。
上游返回片段是**间歇性**的（实测过同一条记录不同时刻返回 720813 B 与 9550125 B 两种结果），
所以这两个分支没法按需复现，只能等它自己出现时再验。

**加了 `main` 之后运维上多的那一件事**：以前构建失败只是不部署、线上不受影响；现在 Worker
抛异常就是线上 500。所以 `src/worker.ts` 里每条路径都有兜底，且非 `/api/music/*` 的请求
一律 `return env.ASSETS.fetch(request)` 原样交回静态资源 —— 静态站的行为一点不变
（已实测：`/` 与不存在的路径分别正常返根路径那一页与 404 页 —— R14 阶段⑥ 之后根路径是起始页，
正站首页在 `/home`）。

这次部署照出两条**以前没记过的线上口径**，都不是本轮改坏的，但都因为本轮才有了实际影响：

**① 静态资源不支持 Range。** 带 `Range: bytes=0-9` 或 `bytes=5000000-5000099` 请求
`/audio/te-bie-de-ren.mp3`，线上一律回 **200 + 整段 10,365,431 字节**，既没有
`accept-ranges` 也没有 `content-range`（`cf-cache-status: HIT`）。图片同理。于是本地这首歌
是**整段下载**的：`preload="none"` 保证点播放之前不下载，点了之后一次拉完 10.4 MB，
拖进度条到还没到的位置要等那一段流过去。以前本地是两段几百 KB 的音垫，这条限制看不出来。
点歌进来的曲目不受影响 —— 那些字节直接从 `m801.music.126.net` 拉，上游支持 206（实测过）。
真要按需分段，只有把音频挪去 R2 并自己写 Range 分支这一条路，而那等于让 Worker 中转媒体
字节，与既定设计相反 —— 先记着，别顺手改。

**② 边缘缓存命中时 `cache-control` 会被改写成 4 小时。** Worker 生成的响应带
`public, max-age=300`，本身是可缓存的，所以它**确实会进边缘缓存**（与「Cache Rules 对
Workers 不生效」是两回事 —— 那说的是规则配不进来，不是默认缓存不工作）。实测：

```
list?…&probe=1..5（每次 URL 不同）  → max-age=300，  cf-cache-status: null
search?q=方大同&n=3 第一次           → max-age=300，  cf-cache-status: null
search?q=方大同&n=3 第二次           → max-age=14400，cf-cache-status: HIT
```

14400 秒＝4 小时，是 zone 上 Browser Cache TTL 的默认值：**HIT 的响应会被它把
`max-age` 抬上去**（`pic` 的 86400 比它长，就原样保留，所以不是无条件覆盖）。
边缘自己的 TTL 仍按源的 300 算，站上表现也不受影响 —— 前端 `api()` 一律
`cache: 'no-store'`，浏览器既不读也不写这条缓存（R23 加的那一半正好挡在这儿）。
但**这条头是给浏览器看的**：哪天前端把 `no-store` 去掉，「改了歌单四小时看不到」
就会以线上独有的形式回来。要根治得去面板把 Browser Cache TTL 改成
「Respect Existing Headers」，那是 zone 设置，等沉麟发话。

同一个模型 20 分钟前还好，再调就「无可用渠道」。三样的值都在本机 `.dev.vars` 里
（那个文件已被 `.gitignore` 排除，`git check-ignore` 验过）。

**R41 起这三个 secret 只是底座。** 后台可以配**最多三条线路**（各有自己的端点、密钥、
协议、模型），按顺序试；它们存在 Durable Object 里，改完下一次对话立刻生效。
这三个 secret 只在「后台那份配置为空或存坏了」时兜底 —— 换服务商不必再动 secret，
更不必重新部署。国内服务商的端点表在 `src/data/providers.ts`（十家，端点实测过），
后台「探一下能不能连」那颗按钮回答「Cloudflare 边缘到这一家通不通」。

后台那把锁两样。**明文口令只出现在你自己的终端里**，哈希才进 secret：

```bash
node -e "const c=require('crypto');const s=c.randomBytes(16);const h=c.pbkdf2Sync(process.argv[1],s,10000,32,'sha256');console.log('pbkdf2$10000$'+s.toString('base64')+'$'+h.toString('base64'))" 你的口令
```

```bash
npx wrangler secret put ADMIN_HASH
```

```bash
npx wrangler secret put ADMIN_SECRET
```

第一条打印出 `pbkdf2$10000$…$…`，粘给 `ADMIN_HASH`；`ADMIN_SECRET` 随便粘一串足够长的
随机字符（cookie 签名用，换掉它等于把所有登录态一次性失效）。**两样缺一样，`/admin`
就锁死而不是开着** —— 页面会显示「还没设口令」并把这三条命令列出来。

迭代数只有一万，是因为 Workers Free 是 10 ms CPU／请求，而这把锁的威胁模型里哈希本身
不可能泄漏（只在 secret 里，不落库、不进仓库），离线爆破的前提不成立。

改口令：重跑生成命令 + 重新 `secret put ADMIN_HASH`，**不需要重新部署**。

### 怎么扫

```bash
# 工作区：本机路径、地名、手机号、邮箱、密钥类字样
grep -rnE '[A-Za-z]:\\(Users|Downloads)|\b1[3-9][0-9]{9}\b|[\w.]+@(qq|163|gmail)\.com' . | grep -v node_modules
grep -rniE 'api[_-]?token|api[_-]?key|secret|password|bearer [A-Za-z0-9_-]{20,}' . | grep -v node_modules

# git 全历史：逐个提交搜，这才是准的
git rev-list --all | xargs git grep -l '要搜的字符串'

# 曾被提交过的凭据类文件（即使现在已删）
git log --all --pretty=format: --name-only --diff-filter=A | sort -u | grep -iE '\.env|credential|secret|\.pem$|\.key$'
```

> **别用 `git log -S` 当扫描手段。** 它只列出**改变了该字符串出现次数**的提交。本次实测：
> `git log --all -S'<地名>'` 只报出 1 个提交，而 `git rev-list --all | xargs git grep -l` 报出
> **8 个** —— 字符串首次引入后一直存在，后续每个版本里都还有，`-S` 一个都不报。
> 据 `-S` 的结果判断「只有那一个提交受影响」会直接漏掉七个。

> **`git grep` 搜历史时不能加 `--`。** `git rev-list --all | xargs git grep -l 'x' --` 会把
> 后面的 SHA 全部当成**路径**（`--` 是「版本到此为止」的分隔符），结果恒为 0 命中，看起来
> 像「历史很干净」。正确写法是不带 `--`。这个假阴性踩过一次。

### 历史重写

本机没有 `git filter-repo`（也没有对应 python 模块），用内置的 `filter-branch`。替换脚本
放在**仓库外**，否则会被 `--tree-filter` 一起提交进去：

```bash
# /tmp/scrub.sh —— 只处理 .md，sed -i 碰二进制会损坏文件
find . -name '*.md' -type f -exec sed -i -e 's/旧串/新串/g' {} +

git bundle create /tmp/backup.bundle --all   # 先备份，并 git bundle verify 一次
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --force --tree-filter 'sh /tmp/scrub.sh' -- --all
```

两个必须知道的行为：

- **`filter-branch` 会把 `refs/remotes/origin/main` 也一起改写**（`-- --all` 的效果）。本地
  记录的远端状态因此失真，push 前先 `git fetch origin` 拉回真实值。
- **它把原始引用留在 `refs/original/` 下**，所以重写之后 `git rev-list --all` 会同时数到
  新旧两套提交（本次 16 → 25），`git grep` 也会在旧的那套里搜出敏感串。**这不是脱敏失败**。
  验证时要么只看 `git rev-list main`，要么先删备份引用：

```bash
git for-each-ref --format='%(refname)' refs/original | xargs -n1 git update-ref -d
git reflog expire --expire=now --all && git gc --prune=now
```

### force push 不等于删除（这次最重要的发现）

**在 GitHub 上，`git push --force` 不会让旧提交消失。** 它们变成 unreachable object 继续
留在服务端，而且**公开状态下匿名可读**。本次实测，仓库公开后：

| 步骤 | 匿名请求 | 结果 |
| :--- | :--- | :--- |
| 1 | `GET /repos/{owner}/{repo}/events` | 200，响应里直接有 `"head": "<force push 前的 SHA>"` |
| 2 | `GET /repos/{owner}/{repo}/commits/<那个 SHA>` | 200，`parents` 字段完整 |
| 3 | 顺 parent 链往上走 | 走到任意一个被重写掉的旧提交 |
| 4 | `raw.githubusercontent.com/<owner>/<repo>/<旧 SHA>/<文件>` | 200，**未脱敏原文原样返回** |

也就是说**不需要猜 40 位 SHA**，调一次 events API 就拿到入口。重写历史的工作在 GitHub 侧
等于白做。

改回私有可以立即止血（上面 1–4 全部变 404），但有个尾巴：`raw.githubusercontent.com` 走
Fastly，响应带 `Cache-Control: max-age=300`，**私有化之后 5 分钟内仍能从 CDN 缓存读到**
（实测 `X-Cache: HIT`；等 `Expires` 过后复验为 `X-Cache: MISS` + 404）。

**结论：想让敏感内容真正不可达，只能换一个从来没存过它的仓库。** 两条路 ——

1. 删掉远端仓库再同名重建（彻底，但删除不可逆）；
2. **新建另一个仓库推干净的历史，旧仓库保持私有**（本次选的路，零删除风险，代价是仓库地址变了）。

选 2 之后要跟着改仓库地址的地方：`src/content/projects/this-site.md` 的 `repo`、
`src/content/kb/is-code-open.md` 的正文、本文档「发布流程」里 Workers Builds 要连接的仓库。
`src/consts.ts` 的 `SOCIAL.github` 指向的是用户主页不是仓库，不用改。

**验收判据不是「本地干净」，是匿名 clone 干净**：

```bash
GIT_TERMINAL_PROMPT=0 git -c credential.helper= clone https://github.com/<owner>/<repo>.git /tmp/verify
cd /tmp/verify && git rev-list --all | xargs git grep -l '敏感串'   # 必须 0 命中
```

**以后的约定**：`docs/` 是公开文档。账号邮箱、本机绝对路径、地名、二维码图片一律不写进去 ——
这类信息对读文档的人零价值，对搜到它的人有价值。「需求原文一律保留」这条原则的目的是不丢
约束，而地名和本机路径不构成任何约束，所以脱敏不违反它。

| 现象 | 根因 |
| :--- | :--- |
| `wrangler deploy` 整体失败 | 某个 `[[routes]]` 的 zone 还是 pending |

| ~~首屏慢~~ | ~~HTML 未做边缘缓存~~ —— 已解决，见「缓存」一节 |
| 推了 GitHub 但网站没更新 | Workers Builds 没接，GitHub 只是代码存放处。上线必须本地 `wrangler deploy` |
| 找不到 wrangler 凭据 | 它在 `%APPDATA%\xdg.config\.wrangler\` 而不是 `~/.wrangler\` |
| PowerShell 报 `unset` 不是 cmdlet／`&&` 不是有效分隔符 | 那是 POSIX shell 语法。PowerShell 用 `;` 分隔、`Remove-Item Env:X` 清变量 |
| 站长认证文件 404 | 放进 `public/` 后没部署。`public/` 的改动同样要走 build + deploy |
| 以为删掉工作区那行就算脱敏了 | git 历史里还在。公开前必须扫历史，见「仓库公开前的脱敏」 |
| `git log -S` 只报了一个提交，误以为只有一处 | 它只列改变了字符串出现次数的提交。实测漏报 7/8，别拿它当扫描手段 |
