## 一、五条接口的契约（前端只认这些，换上游不用改前端）

| 路径 | 参数 | 成功响应 | 缓存 |
|---|---|---|---|
| `/api/music/list` | `id`（白名单内歌单 id） | `{ items: JukeTrack[] }` | `max-age=300` |
| `/api/music/search` | `q`、`n`（1–30） | `{ items: JukeTrack[] }` | `max-age=300` |
| `/api/music/url` | `id`、`source` | `{ url, verified?, bytes?, short?, preview? }` | `no-store` |
| `/api/music/pic` | `id`、`source`、`song` | `{ url }`（图片地址） | `max-age=86400` |
| `/api/music/lyric` | `id`、`source`、`song` | `{ lyric, tlyric }` | 有词时 `max-age=86400`，否则 `no-store` |

`JukeTrack` 的形状在 `src/data/jukebox.ts`：`songId / title / artist / album /
urlId / lyricId / picId / source / sign`。

**兼容旧队列**：`sign` 字段现在只是「旧前端标记」，不参与任何授权校验；
旧记录里的 `picId` 是图片 id，取封面时按 `song` 反查歌曲，所以老歌单还能用。

**错误语义**（前端直接显示这些中文，不区分内部细节）：

| 状态 | 含义 |
|---|---|
| 400 | 参数不对（缺参、id 非法、关键词超长、歌单不在白名单） |
| 403 | 上游明确说这首不可匿名播放（会员/版权/地区） |
| 422 | 旧曲源（如 tencent）暂不支持，提示重新搜索 |
| 502 | 上游连不上 / 返回结构不对（绝不外泄上游原文） |

## 二、为什么「音频字节不进 Worker」，以及为什么是浏览器直取

这是本站的既有规矩（见 `docs/开发备忘` 里 `/api/music` 那段），但 2026-11 这轮给出了
新的、更硬的证据。

**旧做法**：Worker 去网易 `player/url` 拿直链，再把地址给浏览器。

**它为什么在线上全挂**：

| 出口 | 同 8 首歌的 `player/url` |
|---|---|
| Cloudflare 机房（线上 Worker） | **8/8 全被拒** |
| 普通宽带 IP | 3/8 拿到直链 |

同一批歌换个 IP 结果就不同 —— 这是**机房 IP 风控**，不是版权判定。
把它写成「会员/版权/地区限制」等于用一句假话掩盖真实故障，用户会被误导到错误的方向。

**现做法**：

```
/api/music/url
  ├─ 先探测中转能否给出真实音频（读前 2KB，验 ID3 / MP3 帧同步 / fLaC / OggS / ftyp）
  │   能 → 返回该地址，浏览器直接播（字节不经过 Worker）
  └─ 不能 → 回退官方 player/url
```

音频字节**从不经过 Worker**：既不受机房 IP 限制，也不占 Worker 流量。
Worker 只在服务端做一次「这个地址真的能返回音频」的确认，避免把 HTML 404 页塞进 `<audio>`。

## 三、外部依赖与风险（换上游先读这段）

当前唯一稳定可播的通道是 `api.injahow.cn`（公共 Meting 网关，响应带 `ACAO: *`）。

**它是外部服务，这是本页最大的单点风险：**

- 它挂了 → 放不了歌（搜索/歌词/封面走官方接口，**不受影响**）
- 它给的是完整音频，不是试听片段
- 前置校验只证明「前 2KB 是有效媒体」，**不证明整首完整、不证明解码播放**

要摆脱这个依赖，唯一干净的路是**自建中转**（自己的机器出网去取官方直链），
代价是一台常开服务器。不自建的话，就把 `src/lib/music/index.ts` 里的
`DIRECT_AUDIO` 换成别的可用网关即可 —— 只改这一处。

**已排除的候选**（都实测过，记在这里免得有人再试一遍）：

| 候选 | 为什么不用 |
|---|---|
| `api.i-meto.com` | 列表/搜索 JSON 正常，**音频 URL 实际 404**。列表 200 ≠ 能播 |
| 官方 `song/media/outer/url` 捷径 | 对多数歌 **302 到 `/404`**（返回 107191 字节 HTML），浏览器报 `MediaError.code 4` |
| 旧 `yinyueku.cn` | 本机 HTTP/HTTPS 均超时，停用（不能据此断言「全站停服」，只能说不通） |
| 浏览器直连官方 `player/url` | 官方接口不返回 CORS 头，`fetch` 直接失败 |

## 四、上游适配细节（`upstream.ts`）

- **两个官方主机**：`music.163.com`、`interface.music.163.com`。只在**网络失败或结构不对**
  时切换；上游明确给出的 403/404 不再换主机（那是判定，不是故障）。
- **歌单补齐**：`/api/v6/playlist/detail` 只展开前几首，但会给出全部 `trackIds`。
  按 100 个一批用 `/api/song/detail` 补齐，**保持原顺序**，上限 330（`LIST_MAX_N`）。
- **超时**：单次 4s、总计 15s，覆盖 headers 与 body 读取。
- **体积上限**：JSON 2 MiB，超了直接判失败并取消 body。
- **媒体前缀校验**：`Range: bytes=0-511`，验 `content-type` 与魔数，
  非 0 起始的 206 视为无效，重定向只允许落到 `*.music.126.net`。

## 五、怎么验

```bash
# 离线（不需要网络，改上游逻辑后先跑这个）
node --test scripts/music-upstream.test.mjs

# 加真实上游探测（会真的打官方接口与 CDN）
$env:MUSIC_LIVE='1'; node --test scripts/music-upstream.test.mjs
```

**但测试通过不等于能听歌。** 播放验收必须在真实浏览器里做，且有三个坑：

1. **不要加 `--autoplay-policy=no-user-gesture-required`** —— 它会掩盖真实行为。
2. **页面有两个 `<audio>`**：带 `controls` 的是装饰性的，**真正出声的是没有 `controls` 的那个**。
3. **`readyState: 0` 不一定是失败**，也可能只是还没调 `play()`；要看 `paused` 与
   `play()` 返回的 Promise。

判据是 `<audio>.currentTime` 在推进、`error` 为 null：

```
搜索「起风了」=> 30 条 → 点第 1 条 => ✅ t=6.88s dur=326s readyState=4 error=null
```

## 六、Worker 侧的接线（`src/worker.ts`）

- `run_worker_first` 必须含 `/api/music/*`，否则请求进不到 Worker（会落到静态 404 页）。
- 只接 GET；`sec-fetch-site` 存在且不是 `same-origin` 时 403（挡外站盗链，
  但挡不住脚本直刷 —— 这是「点歌全公开」的既定代价，别当成安全边界）。
- 边缘缓存用 `caches.default`，缓存键带 `__music_schema=MUSIC_CACHE_VERSION`，
  换了上游语义就升这个版本号，避免把旧结构当命中。
- 静态音频（`/audio/*.mp3`）仍然由 `env.ASSETS` 直发，不经过这里。
